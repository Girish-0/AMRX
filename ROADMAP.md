# Roadmap

**All engineering gates are open.** This plan summarizes [v2 §12–13](docs/engineering/roadmap-v2.md). It is an ordered evidence plan, not a promise of dates or capacity. Owner roles come from v2; named assignments and schedules need team agreement.

| Gate | Outcome | Completion evidence | Owner role |
|---|---|---|---|
| G0 | Confirm requirements and access | Current organizer requirements, scope/originality clarification, working Fusion access and tested public design-link access | Integration lead + faculty/SPOC |
| G1 | Establish one configuration | Parameter sheet, mass boundaries, Part A/Part B CAD, handling and service envelopes without collisions | Part A + Part B leads |
| G2 | Review loads and ground support | Checked free-body diagrams, mass/CG ledger, wheel reactions and stability results under the declared envelope | Analysis lead + mechanical mentor |
| G3 | Prove the interface specimen | Tolerance/section drawings, seating/retention records, support adjustment and repeatability measurements | Interface lead |
| G4 | Compare structures fairly | Reproducible global/local studies, joint checks and conventional baseline with matched boundaries | Analysis + CAD leads |
| G5 | Establish manufacturing feasibility | Process-specific drawings, slicing/orientation, finishing and inspection plan, access/quotes | Manufacturing lead |
| G6 | Demonstrate stationary workability | Restrained low-load exchange, cargo transfer, retention and fault-response records | Part B + controls leads |
| G7 | Optional low-speed mobility | Supervised contained trials, incremental loads and measured stop behaviour | Controls lead + competent supervisor |
| G8 | Develop capacity/endurance evidence | Full-scale process-appropriate hardware, fixtures and strength/endurance records | Faculty/industry engineering support |

The immediate work is G0–G3. G4/G5 should use the configuration and interface evidence they depend on. G6 follows manufacturing and approved test preparation. G7/G8 are later extensions, not evidence implied by a scaled demonstration.

## Working backlog

Use [GitHub Issues](https://github.com/Girish-0/AMRX/issues) for gate work. Every issue should identify the gate, deliverable, acceptance evidence, dependency and owner. Close it only after a reviewed evidence link is available. One issue can coordinate a gate while smaller tasks are linked beneath it.

## Release policy

The first repository milestone is a **documentation baseline**, not a robot release. A future design release needs a reviewed configuration, drawings/native project, evidence index, limitations and approval record. Software versions should begin only when software exists; do not label the concept a production release.

Automatic exchange, custom navigation/fleet software and further powered attachments stay deferred unless a reviewed scope decision changes the baseline.
